    Definition

    Detailed Java design for cooperative task execution and the TimingSystem-scoped coordination pattern used by domain.system.TimingSystemConductor.

    Both coordinators are labeled Conductor in Figure SI01-01, one in the Application layer and one inside TimingSystem. Their Java implementations are application.ApplicationConductor and domain.system.TimingSystemConductor.

    Some operations consist of several ordered steps. One step must stay short enough to release the shared worker; an elapsed-time wait or asynchronous dependency must not hold that worker. SerialTaskRunner provides that execution policy while concrete work implements YieldingTask.

    YieldingTask.runStep()
        |
        v
    TaskStep
 /      |       |       \
AGAIN AFTER(t) AWAIT(c) DONE
  |      |       |       |
  |      |       |       +--> complete this run
  |      |       +----------> completion callback; later re-admit
  |      +------------------> JDK timer; later re-admit
  +-------------------------> submit next step at executor queue back

    SerialTaskRunner owns runner-local bounded pending-step admission plus a reference to the Runtime-owned single-thread ScheduledExecutorService. One submitted TaskRun step executes exactly one runStep(). AGAIN submits the same run's next step at the executor queue back. AFTER(delay) uses the JDK scheduler as a timer and submits the next step only after the delay. AWAIT(completion) registers an asynchronous completion callback and submits the next step only when that dependency finishes. DONE completes the run.

    There is no task-specific serial-lane layer between a cooperative task and the JDK scheduler. Delays and asynchronous waits control when a TaskRun becomes eligible again and consume no runner pending-step slot while waiting.

    AbstractTask is the reusable lifecycle owner for recurring state machines. A concrete task still owns its operation state; the base class only owns run/wake mechanics:

    event/request/completion
        |
        v
 AbstractTask.wake(SerialTaskRunner)
        |
        +-- no run active ----> resetForRun() + SerialTaskRunner.runTask(...)
        |
        +-- run active -------> remember one pending wake

run completes
        |
        +-- success + wake pending --> start one fresh current-state run
        +-- otherwise ---------------> idle

    Repeated wakes during one run therefore coalesce into one follow-up run. Cancellation drops the pending wake and cancels the current run. The concrete runStep() reads current state; event payloads are not replayed as an implicit queue of state-machine transitions.

    The responsibilities are:

    YieldingTask
  one cooperative step contract
  component/operation state remains in the concrete task

TaskStep
  continuation decision: AGAIN / AFTER(delay) / AWAIT(completion) / DONE

AbstractTask
  reusable run lifecycle, wake coalescing, cancellation and completion hook

SerialTaskRunner
  bounded cooperative pending-step admission directly on one JDK scheduler
  JDK-timer and asynchronous-completion continuation
  optional caller-side bounded wait support

SerialLane<T>
  one typed bounded FIFO, one fixed queue worker, batching and metrics

RuntimeExecutors
  physical role-executor creation, sharing and lifecycle

    Antenna control is a concrete consumer. AntennaManager owns a reusable main AbstractTask plus reusable SelfTestTask, InventoryTask and AntennaShutdownTask. Inventory requests and child-task completions wake the main task; the later step derives the next transition from current manager/device state.

    InventoryTask drives requested inventory state to applied device state and owns power preparation, initialization, direct-antenna start/stop and multiplex rotation:

    InventoryTask
  POWER_ON
      |
      +-- AFTER(powerStabilization)
      v
  INITIALIZE
      |
      +-- AGAIN
      v
  START_DIRECT / START_GROUP
      |
      +-- AFTER(inventoryInterval) when multiplexing
      v
  SWITCH / DONE

    Each TimingSystemConductor owns a MainTask extends AbstractTask executed by its SerialTaskRunner. TimingNode.PROPERTIES.CHANGED only wakes that task. The later run reads every TimingNode's current functional state, derives inventoryRequired = any node OPEN, and calls the optional AntennaManager.setInventoryRequired(boolean).

    The call records desired inventory state without waiting for hardware. Repeating the same value is idempotent and does not become an implicit retry. Explicit repeated engineering requests remain separate retry attempts owned by AntennaManager.

    The cooperative model is optional. A component that only needs typed FIFO item processing uses a normal SerialLane<T>. A TimingNode Data Lane is such a lane. Its Task Lane uses SerialTaskRunner because startup and upstream work can yield or await another lane. Delayed/cooperative capability is composed only where it has a concrete responsibility.

    A device/provider implementation may itself use the same pattern when its protocol requires multiple commands, waits or retries. That state machine remains inside the device boundary. No parent may block a shared worker while waiting for work that still requires that worker or the same serial lane.

    This model realizes the SSD requirement for component-local ordered execution with a small, measurement-driven number of physical workers. It does not change component ownership or add parallel execution within one serial lane.
