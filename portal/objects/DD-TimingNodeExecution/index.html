    Definition

    Detailed design for TimingNode ordered execution, durable TimingData commit, passive LogBookData reads and the local Event/EventSource publication boundary.

    The Java design uses composition rather than an ActiveObject inheritance hierarchy. One TimingNode owns two logically independent bounded serial lanes:

    TimingNode
  ├── PropertyContainer
  │     ├── functionalState -> transient CLOSED / OPEN
  │     └── locationId -> current LocationId or none
  ├── Data Lane  -> LogBook facade
  │                ├── LogBookDataLane -> SerialLane ordering/wait/rejection mapping
  │                ├── LogBookOperations -> commands, TimingData creation, persistence + commit
  │                └── LogBookState -> recovery state + LogBookData records
  └── Task Lane  -> NodeService
                   -> NodeServiceState, RaceDataState,
                      TeamAssignments, StageStartTimes,
                      UniqueTeamRegistrations
                   -> StageTiming, upstream coordination + heartbeat

    The Data Lane is the sole writer for the append-only TimingData source. LogBookDataLane adapts the generic SerialLane to the LogBook result contract (startup scheduling, ordered submit/wait, reentrancy prevention and OperationException mapping) without creating another queue or thread model. LogBookOperations owns state-changing domain operations, TimingData creation, time capture, durable append, startup reconstruction and commit metrics/logging. LogBookState contains only passive mutable state and committed in-memory TimingData. The persisted TimingData load runs as the first ordered Data Lane task. A successful load publishes the immutable initially loaded TimingData; each later successful commit publishes the committed TimingData record. TimingNode republishes those records but does not use NODE_OPEN/NODE_CLOSE commits to drive functional state. Functional state is changed directly by open()/close(); LogBook failures are reported separately and do not change functional state or LocationId.

    The Task Lane is the sole writer for live RaceData and its derived timing state. NodeServiceState owns RaceDataState, TeamAssignments, StageStartTimes, UniqueTeamRegistrations and the committed TimingData view used by Task Lane-derived timing. NodeService owns the service/lifecycle boundary and executes StageTiming queries on that state. Initial-loaded/committed TimingData facts rebuild or incrementally update that derived state.

    RACE_DATA therefore does not cross to the Data Lane: sequence validation, transactional live-state mutation and ACK happen on the Task Lane. TIMING_DATA REQ/replay is different because its source is Data Lane-owned LogBookData; that path uses bounded asynchronous handoff and immutable history batches. No lane blocks on a Future belonging to the other lane while they may share one physical worker.

    Why composition instead of an ActiveObject base class

    A reusable base class such as TimingNode extends ActiveObject<Work> is possible, but it would couple the domain type to one threading mechanism. Composition keeps that choice replaceable and lets the public TimingNode API stay synchronous and domain-oriented.

    For state-dependent operations the caller uses the result-bearing LogBook path; device or callback ingress may use the fire-and-forget path:

    final class TimingNode {
    private final LogBookAccessor logBook;

    LogBookAccessor logBook() {
        return logBook;
    }
}

TimingNodeTypes.OpenResult opened =
        node.logBook().process(LogBookCommands.open(locationId));

node.logBook().execute(
        LogBookCommands.addAutomaticRegistration(registrationId, time));

// LogBook is the Data Lane component boundary.
// LogBookDataLane owns LogBook-specific lane execution mechanics.
// LogBookOperations owns state-changing command/commit work.
// LogBookState owns passive state and committed TimingData; LogBookStatus owns published status.
// NodeService owns Task Lane service/lifecycle/orchestration.
// NodeServiceState owns passive RaceData/derived timing state.
// UpstreamHandler consumes only the narrow UpstreamTaskState port.

    The visible TimingNode delegates execution mechanics to its child components. execute(command) returns after queueing and has no synchronous domain result. process(command) and process(query) are the result-bearing boundary. An ORDERED query waits for its Data Lane turn; a CURRENT query may read an already safely published snapshot directly. The word process therefore denotes "handle this request and return its result", not "always enqueue this request". Callers use the intentional child boundary rather than reaching into mutable state.

    The important split is:

    open(locationId) / close / consistency-sensitive query
    -> queued internally
    -> execute against current ordered TimingNode state
    -> caller receives processed domain result

device/callback ingress that is explicitly offer-only
    -> bounded queue result
    -> callback may continue immediately
    -> later processing has no synchronous caller waiting for its domain result

    A queue result is never used as a substitute for the domain result of a state-dependent command.

    The Future used to connect the queued work with a waiting caller is an internal Active Object mechanism. It does not appear in the normal TimingNode application/domain interface. The current synchronous caller contract needs only an internal plain Future<R>; CompletionStage is not required.

    Code already running on the Data Lane uses direct private/domain methods such as doOpen() rather than calling the blocking public open() method again. Re-entering a public blocking operation from the same serial lane would wait on work that cannot run until the current work item finishes.

    Operation results and execution failures

    Keep domain outcomes separate from failures of the execution boundary.

    For example:

    OpenResult
  OPENED
  ALREADY_OPEN

RegistrationResult
  COMMITTED
  NODE_NOT_OPEN

OperationException.Reason
  BUSY
  UNAVAILABLE
  FAILED
  INTERRUPTED
  TIMEOUT

    Normal processed outcomes stay in the operation result type. For example, NODE_NOT_OPEN is a normal registration result and does not mean execution failed. Queue-full, unavailable/stopped execution, internal execution failure, interruption and wait timeout mean the caller did not obtain that normal result and therefore use OperationException.

    A timeout is different from a definite rejection. It means only that the caller did not receive the processed result within the configured guard time. TimingNode timeout handling must not automatically cancel or interrupt an already accepted state change. The caller must treat the final outcome as unknown and re-query the current state before assuming that the command did not happen.

    TimingNode uses one small caller-visible OperationException with a stable Reason instead of leaking TimeoutException, ExecutionException or InterruptedException from java.util.concurrent through the domain API. Result-bearing public TimingNode operations explicitly declare throws OperationException, even though the current Java type is unchecked, so callers can see the second outcome family directly at the method boundary. Internal LogBook recovery/lane readiness is not a caller precondition: ordered node operations wait behind startup loading, and any resulting execution failure is reported through the TimingNode operation contract.

    Keep the exception family small and add distinct exception types only where callers need different recovery behaviour. Timeout remains a distinct reason because its outcome semantics differ from a definite not-queued result.

    The Java baseline uses separate wait guards for the two result-bearing LogBook operation families:

    TimingData commit command
  OPEN / CLOSE / AUTO_REG / MAN_REG / REV
  default caller wait guard: 5000 ms

ORDERED LogBook query
  count/range/recovery reads that enter the Data Lane
  default caller wait guard: 2000 ms

CURRENT LogBook query
  published immutable/current snapshot
  no Data Lane wait timeout

    The 5000 ms commit value is a guard on how long the synchronous caller waits for the complete ordered commit result. It includes time already queued ahead of the command plus command execution, durable append, in-memory commit and result delivery. It is not a statement that one file append is allowed to consume five seconds. Normal local persistence is expected to complete far faster; a timeout is an operational failure signal.

    An accepted command is not cancelled when this caller wait expires. The Data Lane may still complete it later, so the caller-visible state-change outcome remains unknown until current state or a later committed fact establishes the result. An ORDERED-query timeout has different meaning: no query result was received within its wait guard, but no state-change outcome is implied.

    These two defaults are explicit composition constants, not one generic operationTimeoutMillis. Runtime configuration is not added solely for tuning before target measurements justify it. Timeout log records include the effective duration so the value is observable when a guard fires.

    SerialExecutor design

    SerialExecutor preserves TimingNode execution semantics while separating the logical bounded lane from the physical worker.

    The logical node-lane topology is:

    Runtime-owned Domain ExecutorService
  ├─ TimingNode A Data Lane -> bounded ArrayBlockingQueue
  ├─ TimingNode A Task Lane -> bounded ArrayBlockingQueue
  ├─ TimingNode B Data Lane -> bounded ArrayBlockingQueue
  ├─ TimingNode B Task Lane -> bounded ArrayBlockingQueue
  └─ TimingSystem Conductor lanes

    Each lane schedules at most one drain token. The physical executor may initially have one worker; a second worker is only justified by measured latency/throughput when blocking persistence is present.

    Only one lane item is processed per drain token. If another node already has a drain token waiting on the shared role executor, it gets an opportunity to run before a busy lane resubmits its next item. This provides fairness at task boundaries without pretending that a single-core Raspberry Pi gains CPU capacity from one Java worker per TimingNode.

    The role executor queue does not buffer registration workload directly. At most one drain token per active lane is scheduled there; workload/backpressure remains in each bounded lane-local ArrayBlockingQueue. The lane always runs on an externally supplied Executor; production supplies the shared role executor and tests own any worker they create.

    Do not replace the lane-local bounded queue with Executors.newSingleThreadExecutor() or another unbounded workload queue; that would hide overload behaviour.

    The project API keeps the two result moments explicit:

    final class SerialExecutor implements AutoCloseable {
    enum AdmissionResult {
        ACCEPTED,
        FULL,
        NOT_RUNNING
    }

    static final class SubmitResult<R> {
        AdmissionResult admission();
        Future<R> futureResult();
    }

    <R> SubmitResult<R> submit(Callable<R> work) {
        // Non-blocking bounded admission.
        // futureResult() exists only when admission() == ACCEPTED.
    }

    AdmissionResult offer(Runnable work) {
        // Admission-only fire-and-forget producer path.
    }
}

    Usage rules:

    • AdmissionResult answers only whether the bounded serial lane accepted the work item;
    • SubmitResult.futureResult() represents the later processed result and is available only for accepted work;
    • ACCEPTED is never interpreted as successful domain processing;
    • offer(Runnable) is for producer paths that intentionally do not wait for a result;
    • TimingNode execute(...) and consistency-sensitive query(...) use the result-bearing path;
    • LogBook queue(...) translates the low-level admission-only path into the Domain QUEUED / QUEUE_FULL / NOT_RUNNING result.

    The JDK executor rejection path is translated into the project FULL / NOT_RUNNING semantics; RejectedExecutionException does not leak into normal TimingNode callers.

    The required behaviour remains:

    • queue capacity is visible and bounded per Data Lane;
    • FIFO order is preserved for one TimingNode;
    • at most one work item from one lane executes at a time;
    • different node lanes share the role worker and make progress at task boundaries;
    • state-dependent validation happens on the ordered node-local lane;
    • result-bearing work has an internal Future;
    • fire-and-forget ingress observes only whether work was queued, without waiting;
    • one ordinary work-item failure does not terminate the lane;
    • an unexpected fatal lane failure is observable and does not shut down sibling lanes or the shared role worker;
    • closing one lane stops new queueing and drains work already queued without closing the externally owned role executor;
    • a fatal lane failure likewise never shuts down that executor;
    • Runtime shuts down the shared role executor only after component lanes have stopped.

    The TimingNode remains the lifecycle owner of both logical serial lanes. SerialExecutor is a Platform primitive and contains no TimingNode/domain/persistence logic.

    Execution measurements are owned by the separate SerialExecutorMetrics class in the same Platform execution executors package. SerialExecutor only records lifecycle/admission/execution facts into that object and exposes it through metrics(). Hot-path updates remain primitive/low-allocation; an explicit metrics().snapshot() call creates the immutable engineering view. Keeping the metrics implementation in a separate source file prevents the executor's queue/lifecycle logic from being obscured by diagnostic state while still keeping the metrics component-owned rather than introducing a second runtime model.

    SerialScheduledExecutor design

    SerialScheduledExecutor is a separate Platform primitive for active objects that need one serial lane plus delayed/periodic work. It is not a subclass of SerialExecutor.

    Production Runtime owns one shared single-worker ScheduledThreadPoolExecutor for the TagProcessor role. Each TagProcessor gets a logical SerialScheduledExecutor lane backed by that worker. The lane provides:

    • immediate serial execution for coalesced processing/control work;
    • fixed-delay housekeeping serialized with that immediate work;
    • cancellation of scheduled work;
    • lane-local lifecycle/diagnostic state.

    A periodic trigger does not execute TagProcessor state concurrently with immediate work: it enters the same logical serial lane, and the next fixed-delay trigger is registered after that lane execution completes. Closing or faulting one lane never shuts down the shared TagProcessor role executor.

    For Java 8 the shared scheduled worker enables setRemoveOnCancelPolicy(true) so cancelled periodic triggers are removed promptly from the delayed queue. SerialScheduledExecutor always receives an externally owned ScheduledExecutorService; tests that need a real scheduler create and shut down that scheduler outside the lane.

    TagProcessor owns its ArrayBlockingQueue<TagObservation> separately. Only coalesced queue drain work, policy-control work and housekeeping enter its scheduled serial lane; there is no executor task per observation.

    SerialScheduledExecutor follows the same observability shape as SerialExecutor, with measurement state in the separate SerialScheduledExecutorMetrics class. metrics().snapshot() returns an immutable lane snapshot. These executor metrics describe only work accepted and executed by the scheduled lane; observation ingress/drop metrics stay owned by TagProcessingMetrics.

    The execution types intentionally differ because their workloads differ:

    TimingNode
  -> SerialExecutor
       bounded command work queue
       result-bearing commands and fire-and-forget queued commands

TagProcessor
  -> bounded TagObservation input queue
  -> SerialScheduledExecutor
       coalesced queue draining
       scheduled housekeeping

    Both are JDK-backed baselines. SerialScheduledExecutor reuses a SerialExecutor internally as its logical serialization lane; this does not add another physical worker. The small lane-drain adapter exists only to preserve per-node bounded ordering on shared JDK role workers; it does not replace JDK thread coordination or scheduling. More complex worker-pool behaviour remains an optimization option only after V01 demonstrates a need.

    TimingData commit

    The queue does not contain a pre-numbered TimingData record. Sequence is chosen on the worker immediately before persistence:

    private void processRegistration(RegistrationInput input) {
    long sequence = logBook.nextSequence();

    TimingDataFactory.Context context =
        timingDataContext(sequence, activeLocationId, input.effectiveTime(), timeSource.now());

    RegistrationId registrationId = input.registrationId();

    TimingData data;
    if (input.isAutomatic()) {
        data = timingDataFactory.createAutomaticRegistration(context, registrationId);
    } else {
        data = timingDataFactory.createManualRegistration(
                context, registrationId, input.timeSource());
    }

    timingDataStore.append(data);    // durable before return
    logBook.add(data);               // committed domain state
    timingDataCommittedEvent.emit(data);
}

    Only the Data Lane worker calls this commit path, so a producer lock around sequence allocation is unnecessary.

    LogBookData.nextSequence() reads committed state and does not consume the value. If append fails, LogBook is unchanged and retry uses the same next sequence. The worker must not process a later timing record ahead of that failed record.

    Node data persistence and passive LogBookData

    LogBookData has no worker thread. It stores immutable TimingData values, but it is contained mutable TimingNode state rather than a globally readable repository.

    Code outside the TimingNode ownership boundary does not read the mutable LogBookData list directly. A consistency-sensitive query enters the Data Lane and performs its bounded read in the same ordering as state changes.

    The read representation is deliberately selected per use-case. Bounded visitor-style IF-03 range/latest queries may traverse owned LogBookData records directly on the Data Lane. The TIMING_DATA synchronization query timingDataRange(fromSequence, limit) instead returns a bounded immutable copy so the same LogBookAccessor query contract can be used without exposing mutable LogBookData. The synchronization batch limit is 256 records. Network write/send remains outside the Data Lane.

    For range/latest/ranking-style access, prefer direct bounded traversal when that avoids unnecessary allocation and GC pressure. A bounded immutable copy is also valid when it makes the component boundary simpler and its cost is controlled by an explicit limit. Compact derived/indexed state or reusable scratch storage remain alternatives when measurements show they are cheaper overall.

    The important guarantees are:

    • each consistency-sensitive read has a defined place in the same ordering as state changes;
    • no external consumer retains a mutable collection owned by TimingNode;
    • normal runtime blocking I/O is not introduced casually on the Data Lane;
    • initial persisted-data loading is the explicit exception: it is the first ordered Data Lane task because it rebuilds LogBook-owned state before later Data Lane commands;
    • Runtime may still serialize those logical node loads on one shared physical Data Lane worker rather than creating parallel filesystem workers;
    • read strategy is selected from measured CPU, allocation/GC and lane-occupancy behaviour rather than convenience alone.

    TimingNode keeps functional state and LocationId as separate generic Property<T> values in one PropertyContainer; there is no Domain Status object in TimingNode. Consumers use the container's normal EventSource<PropertyUpdate> change source rather than one Event implementation per property.

    Functional state starts CLOSED with no LocationId. Persisted or newly committed NODE_OPEN/NODE_CLOSE TimingData does not update functional state. TimingNode lifecycle operations apply functional state independently from whether the separate NODE_OPEN/NODE_CLOSE TimingData record later commits successfully.

    Functional state/LocationId are intentionally not restart-durable in the current design. A later design may reconstruct or persist them separately; that is a separate architecture decision rather than an implicit LogBook recovery responsibility.

    Node data persistence boundary

    Use a separate persistence boundary for each state type whose history/snapshots need to be kept:

    Store Purpose Commit role
    TimingDataPersistence append/load canonical TimingData durable append is required before LogBookData visibility; source for LogBookData rebuild
    per-type persistence components preserve accepted analysis history/snapshots do not make the lower storage layer own domain semantics

    The lower I/O layer exposes storage mechanics rather than domain-specific store interfaces. The current Java persistence split is:

    Domain
  DefaultTimingDataPersistence
    - TimingDataCodec
    - TimingNodeId validation
    - sequence validation
           |
           v
I/O
  AppendOnlyRecordStore
           ^
           |
  FileAppendOnlyRecordStore
    - LF/CRLF framing
    - incomplete-tail repair
    - directory/file handling
    - FileChannel.force(true)

    Runtime composition creates the file store and supplies it to DefaultTimingDataPersistence. No class under io.storage imports a Domain or Application class.

    The Data Lane worker fixes the order in which state changes execute against the node-owned state. The current design may call the small/infrequent analysis-store writes on the same worker. If measurements show that one of those writes delays registrations, the worker can hand an immutable snapshot to a bounded storage executor. Do not add one thread per state object and do not introduce an unbounded background queue.

    For the registration path, synchronous persistence on the node lane remains the baseline: producer callbacks return after the command is queued, while the shared Domain worker performs the durable append before LogBook/event visibility. Because that physical worker is shared, a long FileChannel.force(true) can temporarily delay other Data Lanes as well. That is an explicit trade-off for the resource-constrained baseline, not an assumption that nodes execute in parallel.

    Characterize store latency, per-lane queue high-water and fairness under the aggregate 20 registrations/s application workload before moving durability work off the shared Domain worker. If the reference Raspberry Pi cannot meet the workload because durable storage stalls the role worker, the next design step is a bounded durability mechanism that preserves commit-before-LogBookData/event ordering; it is not to multiply the stress target per node.

    For example, an ordered RACE_DATA message containing a StageStartTimes change remains entirely on its owning Task Lane:

    Task Lane / UpstreamHandler
  -> validate NodeId + sequence
  -> RaceDataState validates changes against copies
  -> atomically replace TeamAssignments + StageStartTimes
  -> advance lastAppliedRaceSeq
  -> enqueue ACK(stream=RACE_DATA, seq=lastAppliedRaceSeq)

    A sequence gap requests the first missing sequence without mutating live state. An invalid change does not advance or ACK the sequence. If received RACE_DATA is not persisted over reboot, the node restarts at sequence 0 and requests the retained stream from 1.

    The cross-lane direction is instead driven by durable TimingData facts:

    Data Lane
  -> persist TimingData
  -> publish LogBookData visibility
  -> emit immutable committed TimingData fact
       |
       +-- bounded Task Lane handoff
              -> update UniqueTeamRegistrations
              -> update Task Lane timing history/view

Data Lane startup load
  -> rebuild LogBook
  -> emit immutable initial TimingData snapshot
       |
       +-- bounded Task Lane handoff
              -> rebuild UniqueTeamRegistrations + timing view

    A full Task Lane handoff must be visible as overload/unavailable derived state; it must never silently produce a stale unique-team count.

    Simple typed events

    Local typed facts/notifications use the small Event<T> abstraction rather than a central event bus. Examples include decoded antenna observations, post-commit TimingData, TimingNode status changes and configuration changes. The reusable mechanism lives under platform.events because it is a small JDK-only primitive rather than domain semantics, external I/O or concrete infrastructure.

    Conceptually:

    interface EventSource<T> {
    boolean subscribe(Consumer<T> listener);
    boolean subscribe(Predicate<T> filter, Consumer<T> listener);
}

final class Event<T> implements EventSource<T> {
    DeliveryReport emit(T value);
}

    A component owns the mutable Event<T> instance and is the only code allowed to emit the fact. Consumers receive an EventSource<T> view, so they can wire a listener without gaining publication rights.

    Event wiring is part of application composition:

    Runtime.create(...)
  -> construct components
  -> subscribe EventSource listeners
  -> wiring complete

Runtime.activate()
  -> components/workers become active
  -> runtime uses emit(...)
  -> no dynamic subscribe/unsubscribe rewiring

    The event graph is therefore fixed before activation. subscribe(...) is a composition-time operation and may include a predicate when a consumer only needs a subset of the published facts. The predicate is evaluated synchronously by the Event before the listener is delivered that value. EventSource deliberately exposes no unsubscribe(...) in the baseline. If a future requirement genuinely needs dynamic connection lifecycle, that requirement must define its ownership and concurrency semantics rather than silently turning every local event into a runtime-mutable graph.

    EventSource<T> always has 0..N notification semantics. Callers do not choose a single-listener or multi-listener event type. The implementation may optimize storage for the common case:

    0 listeners  -> null / no listener container
1 listener   -> Consumer<T> directly
2+ listeners -> immutable Consumer[] in subscription order

    That 0/1/N representation is only an allocation/memory optimization. It does not change the public 0..N semantics.

    For committed TimingData the component owns an explicitly named post-fact event:

    private final Event<TimingData> timingDataCommittedEvent = new Event<>();

public EventSource<TimingData> timingDataCommittedEvent() {
    return timingDataCommittedEvent;
}

    The commit path is therefore:

    Data Lane
  -> persist TimingData
  -> update committed LogBook state
  -> timingDataCommittedEvent.emit(timingData)
       |
       +--> subscribed listener
       +--> subscribed listener

    Delivery is synchronous on the emitting thread and Event<T> does not serialize concurrent emit(...) calls. The completed listener graph is read-only during runtime. Committed-TimingData events originate from the Data Lane after durable commit. TimingNode PROPERTIES.CHANGED originates from PropertyContainer.update(). One logical update emits one PropertyUpdate containing the complete list of changed properties. For OPEN, LocationId and functional state are both current and are reported together in that message.

    Property identity is represented by typed immutable PropertyKey<T> values. The owner keeps the mutable Property<T> handle private while consumers may use the public key to inspect or filter a PropertyUpdate without string-name comparisons. A filtered EventSource subscription does not create another Event or another property publication path; it only suppresses delivery of updates that are irrelevant to that subscriber. TimingSystemConductor therefore listens to TimingNode.PROPERTIES.CHANGED with a filter for the functional-state key and is not woken by unrelated property updates.

    Ordinary listener RuntimeExceptions are isolated and reported in the delivery report so one failing listener does not prevent later listeners from seeing the fact. Fatal Errors are not swallowed.

    Listeners must not become alternate owners of component mutable state. A listener must also remain short and non-blocking. Slow network delivery, retry or persistence work hands the immutable value to its own bounded mechanism and returns. A WebSocket or transport adapter therefore never uses the Data Lane as its backpressure mechanism.

    If listener notification fails after a TimingData record is committed, that does not roll back the commit. A consumer that needs reliable recovery uses authoritative persisted/LogBookData state and its own recovery/delivery mechanism.

    State events may wake the owning control task. The task rereads CURRENT state and computes its desired outcome directly. For inventory, it publishes through AntennaSettings.update(...), and the AntennaManager reconciles that desired value to applied device state on its own lane. Passive Setting<T> owns no executor or source reread mechanism.

    Use onXxx(...) for listener/handler methods, for example onTimingNodeStatusChanged(Status status). Do not introduce a parallel callback registration API such as onChange(Consumer<T>), addListener(...) or setCallback(...) when EventSource.subscribe(...) expresses the notification.

    Other local events may use the same abstraction when a real consumer needs them. Do not introduce events merely to replace an ordinary direct method call to one owned component.

    Multiple TimingNodes

    A TimingNode has one independent Data Lane and one independent Task Lane. Each lane uses its own bounded FIFO; other nodes have separate queues and state owners. The lanes share a Runtime-managed physical executor pool rather than creating one thread per node or per responsibility. This guarantees ordering and node ownership, but not simultaneous execution on a single physical worker. Runtime characterization verifies queue fairness and checks slow-persistence impact on protocol/heartbeat latency.
