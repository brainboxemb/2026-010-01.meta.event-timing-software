    Definition

    Detailed design for TimingNode ordered execution, durable TimingData commit, passive LogBookData reads and the local Event/EventSource publication boundary.

    The Java design uses composition rather than an ActiveObject inheritance hierarchy. One TimingNode owns two logically independent bounded serial lanes:

    TimingNode
  ├── PropertyContainer
  │     ├── functionalState -> transient CLOSED / OPEN
  │     ├── operationalState -> node execution INIT / OK / ERROR
  │     └── locationId -> current LocationId or none
  ├── Data Lane -> TimingNodeDataLane -> SerialLane<TimingNodeDataItem>
  │                └── LogBook
  │                     ├── LogBookDataLane -> result/wait/rejection mapping
  │                     ├── LogBookOperations -> commands, persistence, recovery + commit
  │                     └── LogBookState -> recovery state + LogBookData records
  └── Task Lane -> SerialTaskRunner
                   ├── TimingNode.MainTask -> startup LogBook recovery
                   └── NodeService
                        ├── MainTask -> LogBook INIT / LOADED / ERROR
                        └── NodeState -> retained live/derived state
                             ├── DataTask -> current head + bounded TimingData range reads
                             ├── StateQuery -> ordered result-bearing reads
                             ├── RaceDataState -> TeamAssignments + StageStartTimes
                             ├── ActiveRegistrations -> ordered registration list
                             └── RegisteredTeams -> unique team set / + - changes

    The Data Lane is the sole writer for normal ordered LogBook commands and queries. TimingNodeDataLane adapts the generic SerialLane<TimingNodeDataItem> to typed LogBook-operation and upstream-turn items without creating another queue or thread model. LogBookDataLane owns result-bearing command/query completion and bounded wait mapping. LogBookOperations owns state-changing domain operations, TimingData creation, record-creation time capture, durable append, recovery reconstruction and commit metrics/logging. Internal registration commands carry absolute times as UTC epoch-millisecond long values; they do not retain TimingTimestamp wrappers. For the default IF-05 profile, effective time is canonicalized to the required 10 ms boundary before the TimingRecord is committed, while recordedAtMillis preserves the full 1 ms record-creation time required by recTime. LogBookState contains passive mutable state and committed in-memory TimingData.

    Persisted TimingData loading is not a Data Lane item. After child activation starts normal Data Lane admission, TimingNode.MainTask calls LogBook.loadPersistedData() synchronously on the same physical node worker. Commands may queue during that load but cannot execute until the MainTask step releases the worker. A successful load publishes LogBookStatus.LOADED; load failure publishes LogBookStatus.ERROR. Status is directly readable and is not another Data Lane query. Each later successful commit publishes the committed TimingData record.

    The Task Lane is the TimingNode's SerialTaskRunner. NodeService.MainTask handles only LogBook availability. NodeState groups the retained Task Lane-owned data while RaceDataState, ActiveRegistrations and RegisteredTeams keep their specialized internal responsibilities. NodeState directly implements NodeStateAccessor and NodeStateTestControl. Normal callers see the read-only accessor; engineering/test composition receives the mutation control separately, without an additional state-wrapper implementation object.

    NodeState owns DataTask and StateQuery as execution helpers. DataTask owns the source cursor, bounded asynchronous LogBook reads and catch-up completion. It reads the current LogBook head and continues from its own nextSequence, fetching missing records with bounded ordered timingDataRange(...) queries through LogBookAccessor and yielding while each Data Lane read completes. StateQuery preserves Task Lane ordering for result-bearing reads and may first yield on DataTask catch-up. The current implementation reads at most 64 TimingData records per batch.

    Later committed TimingData does not pass through NodeService or NodeState as a second history collection. The post-commit event only wakes DataTask; DataTask then catches up from the LogBook source. NodeState groups the current live and derived data but does not duplicate committed TimingData.

    ActiveRegistrations stores one ordered compact scalar entry per committed registration ADD. TimingData is consumed at the input boundary and is not retained: the row keeps only sequence, effective epoch milliseconds, packed RegistrationId, numeric LocationId and validity. Its original sequence and WP are stable. A matching REV marks the newest matching valid ADD invalid rather than removing it from the display list; nonregistration records are ignored. Semantic TimingData value objects are reconstructed only for read/output boundaries. The display may visit all registrations for one WP in original source order, including invalid entries, and is responsible for tracking which rows it has shown. A bounded visitAfter(locationId, afterSequence, limit, visitor) pages through later ADD rows using the original registration sequence, avoiding repeated delivery of earlier rows. This cursor does not detect later revocations of earlier ADDs: the display also needs to revisit its already displayed rows to observe changed validity. Domain owns neither the display cursor nor a second per-display update index.

    RegisteredTeams maintains the unique-team set of the currently open WP. The LocationId is scope of the whole projection rather than a key repeated in each retained row/map. Occurrence counts are still kept per RegistrationId so a live assignment change can move all existing occurrences to the newly resolved TeamId. The complete visitor supports the compact full synchronization burst; team order has no domain meaning and the CAN bitmap is independent of visitation order. Only post-rebuild zero-to-nonzero and nonzero-to-zero membership transitions produce incremental + / - notifications. Historical reconstruction itself is silent: the display first takes a full burst after the OPEN projection has caught up. CAN encoding, delivery and per-display synchronization state remain outside Domain.

    Stage-start interpretation is split deliberately between ingress normalization and StageTiming. NodeService.applyRaceData(...) samples the shared TimeSource once and normalizes every IF-06 SET to one compact UTC long before it enters RaceDataState. A time-only value retains only UTC HHmmsscc and therefore remains below 100000000; a value that contains a date is stored as UTC yyyyMMddHHmmsscc. No missing date is added.

    Absolute IF-06 values already define their UTC instant. Local date/time values use the configured TimeSource zone and reject ambiguous/nonexistent DST wall times. A time-only value uses only the zone offset active for the sampled timing context; the result remains time-only. If a variable-offset zone has a transition within the relevant twelve-hour window, the time-only value is rejected rather than guessing which offset applies.

    StageTiming is the single elapsed/rollover rule. For a dated start it compares the explicit UTC date/time directly with the absolute registration passage. For a time-only start it evaluates same-UTC-day/previous-UTC-day rollover and accepts only the unique interpretation with 0 <= elapsed < 12 hours. Exactly twelve hours or otherwise unresolvable values remain known stage starts but do not produce elapsed time or rank.

    The domain.node.registration package contains only active-WP registration-derived state. It is not a second history store. The LogBook remains authoritative for all LocationIds and all earlier OPEN/CLOSE periods.

    While the TimingNode is CLOSED there is no usable registration projection. On OPEN(locationId), NodeState/DataTask clears the previous projection and scans the complete LogBook from sequence one in bounded batches. ActiveRegistrations admits only registration ADD/REV records whose LocationId equals the newly open WP. Therefore older registrations from earlier OPEN periods of the same WP return, while historical rows of every other WP are excluded. On CLOSE the derived projection is deactivated and cleared; reopening the same WP rebuilds it again from LogBook rather than relying on stale retained history.

    Because LocationId scopes the whole active projection, an ActiveRegistrations.Registration row stores only sequence, effective time, packed RegistrationId and validity. Rows remain in original ADD sequence order. A matching REV searches newest-to-oldest and marks the newest still-valid row with the same RegistrationId and effective timestamp invalid; the row is not removed because a display may already have shown it.

    RegisteredTeams is the second active-WP projection. It counts valid occurrences by RegistrationId and resolves those counts through current RaceData to one unique TeamId set. Repeated passages change only occurrence counts. A live assignment change can move all active occurrences for one RegistrationId. Historical replay after OPEN suppresses +/- events until DataTask has caught up; the full team visitor supplies the synchronization snapshot. Only later live zero-to-nonzero and nonzero-to-zero transitions publish incremental events.

    Open/close requests may supersede a pending bounded LogBook read. DataTask therefore treats the requested LocationId as a generation: an obsolete partial batch is discarded, both projections are reset, and the newest requested WP restarts from sequence one. NodeStateAccessor reads wait for that reconstruction/catch-up before observing the projection. Its registration/team read methods take no LocationId because there is exactly one current OPEN scope.

    These objects remain Task Lane-owned. CAN encoding, display cursor/synchronization state, persistence, elapsed-time result models and ranking calculations are outside this package.

    Do not add a production query/result type merely because a unit or integration test would be easier to write with it. A new calculated view belongs in production only when an actual application, presentation or I/O consumer requires that behavior. Tests verify the retained state through the existing production boundary or package-local implementation tests rather than defining extra public API.

    A failed persisted-data load leaves LogBook in LogBookStatus.ERROR with the concrete failure retained in LogBook diagnostics. The TimingNode MainTask still completes its own startup path to operational OK; TimingNode.ERROR is reserved for failure of the node's own startup/execution path. Neither condition replaces functional OPEN/CLOSED state or current LocationId.

    RACE_DATA therefore does not cross to the Data Lane: packet duplicate detection, compact UTC stage-start normalization, transactional live-state mutation and downstream RECV completion happen on Task Lane task turns. TIMING_DATA_REQ/replay is different because its source is Data Lane-owned LogBookData; that path uses bounded asynchronous handoff and bounded TimingData batches. A cooperative task that needs a Data Lane query uses LogBookAccessor.submit(...) and TaskStep.await(...); it never blocks the shared worker waiting on that completion.

    Why composition instead of an ActiveObject base class

    A reusable base class such as TimingNode extends ActiveObject<Work> is possible, but it would couple the domain type to one threading mechanism. Composition keeps that choice replaceable and lets the public TimingNode API stay synchronous and domain-oriented.

    For state-dependent operations the caller uses the result-bearing LogBook path; device or callback ingress may use the fire-and-forget path:

    final class TimingNode {
    private final LogBookAccessor logBook;

    LogBookAccessor logBook() {
        return logBook;
    }
}

TimingNodeTypes.OpenResult opened =
        node.logBook().process(LogBookCommands.open(locationId));

node.logBook().execute(
        LogBookCommands.addAutomaticRegistration(registrationId, time));

// LogBook is the Data Lane component boundary.
// LogBookDataLane owns LogBook-specific lane execution mechanics.
// LogBookOperations owns state-changing command/commit work.
// LogBookState owns passive state and committed TimingData; LogBookStatus owns published status.
// SerialTaskRunner owns cooperative TaskRun execution for the TimingNode Task Lane.
// NodeService.MainTask handles LogBook status and input-processing coordination.
// NodeState implements NodeStateAccessor and NodeStateTestControl; Runtime exposes them separately.
// DataTask rebuilds/catches up the OPEN-WP projection; StateQuery preserves ordered reads.
// ActiveRegistrations owns ordered ADD rows and validity for the currently open WP.
// RegisteredTeams owns the current open-WP unique-team set and live + / - changes.
// Calculated presentation/query models are added only for an actual production consumer.
// DownstreamDelivery invokes NodeService.applyRaceData(...) synchronously on the Task Lane
// before confirming the containing DN_PACKET.

    The visible TimingNode delegates execution mechanics to its child components. execute(command) returns after queueing and has no synchronous domain result. process(command) and process(query) are the result-bearing boundary. An ORDERED query waits for its Data Lane turn; a CURRENT query may read an already safely published snapshot directly. The word process therefore denotes "handle this request and return its result", not "always enqueue this request". Callers use the intentional child boundary rather than reaching into mutable state.

    The important split is:

    open(locationId) / close / consistency-sensitive query
    -> queued internally
    -> execute against current ordered TimingNode state
    -> caller receives processed domain result

device/callback ingress that is explicitly offer-only
    -> bounded queue result
    -> callback may continue immediately
    -> later processing has no synchronous caller waiting for its domain result

    A queue result is never used as a substitute for the domain result of a state-dependent command.

    The Future used to connect the queued work with a waiting caller is an internal Active Object mechanism. It does not appear in the normal TimingNode application/domain interface. The current synchronous caller contract needs only an internal plain Future<R>; CompletionStage is not required.

    Code already running on the Data Lane uses direct private/domain methods such as doOpen() rather than calling the blocking public open() method again. Re-entering a public blocking operation from the same serial lane would wait on work that cannot run until the current work item finishes.

    Operation results and execution failures

    Keep normal semantic results small and owned by the boundary that defines them.

    For example:

    TimingNodeTypes
  FunctionalState
  OpenResult
  CloseResult

Application
  CommandResult
    COMMITTED
    NODE_NOT_OPEN

LogBook command result
  TimingData

    CommandResult belongs to Application because it describes a presentation-triggered command, not TimingNode state and not a LogBook commit primitive. A LogBook registration/revocation command returns the committed TimingData directly. The proxy adds the normal application result around that value and decides NODE_NOT_OPEN before the LogBook is called.

    Technical queue rejection, unavailable execution, interruption, timeout and execution failure are not another TimingNode result/state enum. The Data Lane retains the bounded wait guards and logs the concrete technical reason where it is known. The Java call aborts normal flow with an ordinary runtime failure. Forwarding Application/Presentation layers do not translate the internal failure taxonomy into a second public reason model.

    A command wait timeout still has an important diagnostic distinction: already accepted work may complete later. The owning Data Lane log therefore records that the final command outcome may be unknown. An ordered-query timeout records only that no query result was obtained. That distinction belongs in retained diagnostics; it does not require a generic public operation-state exception.

    Exceptions are not grouped into TimingNodeTypes. That source-only grouping is for actual TimingNode value/result types. Introduce an owner-specific exception only when callers genuinely need distinct programmatic recovery behaviour; otherwise ordinary Java runtime failure plus owning-boundary diagnostics is preferred.

    The Java baseline uses separate wait guards for the two result-bearing LogBook operation families:

    TimingData commit command
  OPEN / CLOSE / AUTO_REG / MAN_REG / REV
  default caller wait guard: 5000 ms

ORDERED LogBook query
  count/range reads that enter the Data Lane
  default caller wait guard: 2000 ms

CURRENT LogBook query
  published immutable/current snapshot
  no Data Lane wait timeout

    The 5000 ms commit value is a guard on how long the synchronous caller waits for the complete ordered commit result. It includes time already queued ahead of the command plus command execution, durable append, in-memory commit and result delivery. It is not a statement that one file append is allowed to consume five seconds. Normal local persistence is expected to complete far faster; a timeout is an operational failure signal.

    An accepted command is not cancelled when this caller wait expires. The Data Lane may still complete it later, so the caller-visible state-change outcome remains unknown until current state or a later committed fact establishes the result. An ORDERED-query timeout has different meaning: no query result was received within its wait guard, but no state-change outcome is implied.

    These two defaults are explicit composition constants, not one generic operationTimeoutMillis. Runtime configuration is not added solely for tuning before target measurements justify it. Timeout log records include the effective duration so the value is observable when a guard fires.

    SerialLane design

    SerialLane<T> is the generic bounded typed FIFO/one-worker primitive. It stores caller-owned values and receives an item processor at construction. The backing Executor sees only the lane's fixed queue-worker runnable.

    The logical node topology is:

    RuntimeExecutors.timingNodeExecutor
  ├─ TimingNode A Data Lane -> SerialLane<TimingNodeDataItem>
  ├─ TimingNode A Task Lane -> SerialTaskRunner
  ├─ TimingNode B Data Lane -> SerialLane<TimingNodeDataItem>
  └─ TimingNode B Task Lane -> SerialTaskRunner

    offer(T) never waits for capacity and returns one of ACCEPTED, FULL or NOT_RUNNING. A successful first offer while idle schedules the one fixed worker. Further offers only extend the lane queue while that worker is scheduled/running.

    One worker run processes at most maxItemsPerRun items that were available at the start of that run. If items remain afterwards, the same worker is scheduled once more. This creates a fairness point for sibling lanes sharing the same physical executor.

    SerialLane does not define application exception policy, result futures or a FAILED lifecycle state. The item owner contains expected domain/runtime failures where required. A backing-executor RejectedExecutionException stops further admission and clears queued items because the lane can no longer guarantee execution. close() stops admission and waits for already accepted work to drain; it never shuts down the Runtime-owned executor.

    Result-bearing domain adapters carry their own completion with the queued item. For example, LogBook query/command items complete their own CompletableFuture; the generic lane remains unaware of command/query semantics.

    The required behaviour is:

    • queue capacity is visible and bounded per logical lane;
    • FIFO order is preserved per lane;
    • at most one worker for one lane is scheduled/running at a time;
    • one worker run processes no more than maxItemsPerRun items;
    • sibling lanes may share one physical worker and make progress at batch boundaries;
    • isExecutingOnCurrentThread() identifies ownership without exposing a lifecycle enum;
    • closing drains accepted work but does not own physical-executor shutdown;
    • Runtime stops physical role executors only after component lanes/runners have stopped.

    ExecutionMetrics provides the shared queue/admission, depth/high-water, queue-wait and execution-duration model. Each SerialLane and SerialTaskRunner owns its own instance; metrics().snapshot() creates the immutable engineering view.

    SerialTaskRunner and direct JDK scheduling

    SerialTaskRunner is an independent cooperative execution primitive. It does not subclass, contain or delegate to SerialLane; it owns runner-local bounded pending-step admission and uses the Runtime-supplied single-thread ScheduledExecutorService directly.

    runTask(YieldingTask) creates one TaskRun and submits its first eligible step. Each executor turn invokes one runStep(). AGAIN submits the continuation at the executor queue back, AFTER uses ScheduledExecutorService.schedule(...) only as a timer, AWAIT attaches an asynchronous completion callback, and DONE completes the run. Delayed/awaiting tasks occupy neither a runner pending-step slot nor the physical worker until their continuation becomes eligible.

    TagProcessor deliberately does not use SerialTaskRunner: observations are plain typed items, so one SerialLane<TagObservation> is sufficient. Its timed filter and housekeeping work runs directly on the same single-thread JDK scheduled executor that backs the observation lane.

    Current composition is:

    TimingNode
  -> Data Lane: SerialLane<TimingNodeDataItem>
  -> Task Lane: SerialTaskRunner
  -> TagProcessor: SerialLane<TagObservation>
                   + direct ScheduledExecutorService callbacks

TimingSystemConductor
  -> SerialTaskRunner
  -> shared timingSystemConductorExecutor

AntennaManager
  -> SerialTaskRunner
  -> sharedIoScheduledExecutor

    SimulatedTagScenarioRunner uses the Runtime-owned sharedIoScheduledExecutor directly. It keeps at most 32 active scenarios and schedules only the next step of each scenario, so simulation work is bounded without another logical lane or scheduling wrapper. A lifecycle-generation guard prevents delayed work from a previous activation from emitting after deactivate/reactivate.

    All execution is JDK-backed. Physical parallelism remains a Runtime decision; adding logical lanes or task runners does not imply adding threads.
